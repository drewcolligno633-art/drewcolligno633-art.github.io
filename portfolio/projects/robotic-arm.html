4-DOF robotic arm

A four-axis arm I designed and built from scratch: custom 20:1 cycloidal reducers on NEMA 17 steppers, a closed-loop driver board in every joint, and control through ROS 2.

Why I built it

I want to work on robot manipulation, and I wanted to understand an arm from the gearbox up rather than only from the software side. So I designed every joint myself, built a driver board into each one, and am bringing it up under ROS 2 one layer at a time. Mechanical design

Each of the four joints is a NEMA 17 stepper motor driving a custom 20:1 cycloidal reducer. Before committing, I compared harmonic drives and cycloidal drives for this size of arm. I chose cycloidal because [your reasons, for example: backlash, torque capacity, how easy it was to make, cost].

Electronics

Every joint has its own SparkFun PD Stepper board. Each board combines an ESP32-S3 microcontroller, a TMC2209 stepper driver, and an AS5600 magnetic encoder that measures the joint's actual position. The boards take power over USB Power Delivery, and the arm now runs from a 12 V supply. I write the firmware in VS Code with PlatformIO.

Control software

The arm is controlled with ROS 2 Jazzy running in WSL2 on my laptop. Each joint board runs micro-ROS, a version of ROS 2 small enough for a microcontroller, and talks to a micro-ROS agent that bridges it onto the ROS 2 network. To move a joint, I publish a target angle on that joint's topic; the board drives the motor there and publishes the angle its encoder reads back.

Problems I solved along the way

  • ROS 2 couldn't reliably find its own nodes

    With WSL2 in mirrored networking mode, the default Fast DDS middleware had discovery problems. I switched the ROS 2 middleware to CycloneDDS, which fixed discovery.

  • The micro-ROS agent had no ARM64 package

    My laptop has an ARM64 (Snapdragon) processor, and the usual snap package for the agent doesn't support it. I run the agent in a Docker container instead. USB devices are passed from Windows into WSL2 with usbipd-win, and each board is addressed by its permanent serial ID so the joints can't swap places when they're plugged in in a different order.

  • The boards negotiated the wrong voltage

    The PD Stepper boards use CFG pins to choose which voltage they request over USB Power Delivery. A misconfigured setting meant the charger wasn't supplying the voltage I expected. [One or two sentences on how you found it and what you changed.]

Where it is now

The first major milestone works: publishing a target angle on /joint1/target_angle moves the joint, and the encoder reading on /joint1/current_angle confirms it got there. All four joint boards are now running and visible in ROS 2.
